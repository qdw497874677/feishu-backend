# Domain Pitfalls

**Domain:** Chatbot conversation flow redesign (state machine + command routing + context binding)
**Researched:** 2026-04-07

## Critical Pitfalls

Mistakes that cause rewrites or major issues.

### Pitfall 1: Adopting Spring Statemachine for Simple State Spaces

**What goes wrong:** Developer sees "state machine redesign" and reaches for Spring Statemachine. SSM requires `StateMachineFactory` to create per-conversation instances, `StateMachinePersister` to save/restore from DB on every message, framework configuration classes, and explicit event-driven transitions. For a 5-state system with simple derived transitions, this adds ~500+ lines of framework boilerplate.

**Why it happens:** SSM is the "obvious" Spring solution for state machines. Its documentation is thorough and it appears well-integrated with Spring Boot. The name matches the requirement.

**Consequences:** 
- Domain layer gains Spring Statemachine dependency (violates COLA framework-agnostic domain principle)
- Each message requires: factory.create() → persister.restore() → process → persister.persist(). That's 2 extra DB round-trips per message.
- Testing becomes harder — state machine configuration must be loaded for unit tests
- Eventual rewrite when team realizes the framework overhead exceeds the domain complexity

**Prevention:** Ask: "Is my state derived or transitioned?" If state is computable from persisted data on each request (binding + session → state), you don't need a state machine framework. You need a state derivation function. SSM is for when states are *transitioned* by events and the transition path matters (order processing, approval workflows).

**Detection:** If the `StateMachineConfiguration` class is longer than the domain logic it protects, SSM is overkill.

### Pitfall 2: Forgetting chatId→threadId Migration on Reply

**What goes wrong:** Session is bound to `feishu:chat:chatId` (because there's no topic yet). The reply creates a new Feishu topic with a new `threadId`. Subsequent user messages in that topic resolve to `feishu:thread:threadId` — which has no binding. The session appears "lost."

**Why it happens:** The binding model doesn't account for Feishu's topic creation behavior. When `TopicReplyStrategy.reply()` creates a topic, the `threadId` is generated by Feishu, not by our system. The binding was made before the reply, so it points to the old context.

**Consequences:** User creates a session via `/oc cn`, gets a reply in a new topic, types a follow-up, and the system says "no session found." This is the #1 reported UX bug.

**Prevention:** After every reply that returns a `SendResult` with a non-null `threadId`, check if it differs from the original `contextRef`. If so, migrate the binding (copy appId + sessionId to the new context).

**Detection:** Test scenario: send `/oc cn prompt` in a group chat with no existing topic → verify the session is accessible from the new topic thread.

### Pitfall 3: Partial State Unification (Keeping Both Enums)

**What goes wrong:** Developer creates the new `ConversationState` enum but leaves `TopicState` and `ContextSessionState` in place "for backward compatibility." Over time, three state systems coexist, each partially used.

**Why it happens:** Fear of breaking existing tests. The 261 tests reference `TopicState` and `ContextSessionState` in mocks and assertions.

**Consequences:** Triple the confusion of the current dual-state problem. New code uses `ConversationState`, old code uses `TopicState`, orchestrator uses `ContextSessionState`. Three different state queries on the same message.

**Prevention:** Unification means removal. When `ConversationState` is ready:
1. Add it alongside old enums
2. Make old enums delegate to new (temporary bridge)
3. Update all call sites and tests to use new enum
4. Delete old enums in the same PR
5. No "we'll clean it up later" — that never happens

**Detection:** `grep -r "TopicState\|ContextSessionState" --include="*.java"` should return zero hits after unification.

## Moderate Pitfalls

### Pitfall 4: Implicit Plain Text Handling in Wrong Layer

**What goes wrong:** Plain text detection ("is this a command or just text?") gets implemented inside `OpenCodeApp.execute()` rather than in the app-layer dispatcher. Now the domain-layer app must know about routing conventions (which messages skip command parsing).

**Prevention:** The decision "this plain text should become a chat prompt" belongs in the app layer (the dispatcher), not in the domain-layer app. The app receives either a structured command invocation or a pre-identified chat prompt — never raw ambiguous text.

### Pitfall 5: Leaking MessageContext into Domain Interfaces

**What goes wrong:** `SubCommandHandler.execute(MessageContext ctx)` causes `MessageContext` (which contains gateway-resolved data) to become part of the domain interface contract. If `MessageContext` gains app-layer fields later, the domain interface is polluted.

**Prevention:** `MessageContext` should live in the domain layer as a pure value object with only domain concepts (state, contextRef, message, sessionId). It must not contain gateway instances, orchestrator references, or Spring beans. Keep it a data carrier — `@Value` with primitive/domain types only.

### Pitfall 6: Race Condition in Binding Migration

**What goes wrong:** Two messages arrive nearly simultaneously. Message A triggers a reply that creates topic T1 with binding migration. Message B arrives in topic T1 before migration completes, finds no binding, and sends "no session" guidance. User sees a confusing "no session" message immediately after creating one.

**Prevention:** Use SQLite's `INSERT OR REPLACE` for binding operations (already recommended in CONCERNS.md). The migration operation should be idempotent. If the binding already exists when Message B arrives, it should find the binding (or wait for it). In practice, at current traffic levels this race is unlikely, but the fix is simple: make binding writes idempotent.

### Pitfall 7: Breaking FishuAppI Interface Contract

**What goes wrong:** Changing `FishuAppI.execute(Message)` to return `OpenCodeExecutionResult` instead of `String`. This breaks all 5 app implementations and their tests.

**Prevention:** The `OpenCodeExecutionResult` pattern applies only to OpenCode's internal execution path, not to the `FishuAppI` interface. OpenCode's `execute()` still returns `String` (or `null`) to the framework. The structured result is used internally between the command router and the app service. Don't change shared interfaces for app-specific needs.

## Minor Pitfalls

### Pitfall 8: Over-Granular SubCommandHandler Splitting

**What goes wrong:** Creating a separate handler class for every command variant: `ChatHandler`, `ChatNowHandler`, `ChatWithSessionHandler`, `ChatWithoutSessionHandler`. 15 handler files for 10 commands.

**Prevention:** Group related commands in one handler when they share significant logic. `ChatHandler` can handle both `chat` and `chatnow` (they differ only in session creation). `SessionHandler` can handle `session status`, `session list`, `sc`. Aim for ~7-9 handler classes, not 15.

### Pitfall 9: Forgetting to Update Help Text

**What goes wrong:** Command behavior changes (new command added, old alias removed) but `OpenCodeApp.getHelp()` still shows old information. Users try commands that don't work or miss new ones.

**Prevention:** Generate help text from the `SubCommandHandler` registry. Each handler provides its help text. The help system assembles them automatically. No manual help string maintenance.

### Pitfall 10: Not Testing State Derivation Edge Cases

**What goes wrong:** `ConversationState.derive()` handles the happy paths but doesn't account for: binding exists but points to a deleted app, session exists but has null data, contextRef is a chat type but with a topicId that looks like a chatId.

**Prevention:** Write exhaustive unit tests for the state derivation function covering all combinations of: contextRef (null, chat, thread) × binding (none, other app, opencode-no-session, opencode-with-session) × session (none, valid, dangling). That's ~15 test cases for a critical function.

## Phase-Specific Warnings

| Phase Topic | Likely Pitfall | Mitigation |
|-------------|---------------|------------|
| Unified state model | Keeping old enums alongside new one | Delete old enums in same PR as unification |
| Context binding migration | Missing chatId→threadId migration | Test the exact scenario: /oc cn in group chat → verify topic binding |
| Command router redesign | Over-splitting handlers | Group by shared logic, aim for 7-9 handlers |
| Plain text routing | Implementing in wrong layer (domain vs app) | Plain text detection in app-layer dispatcher, not domain app |
| Card integration | Assuming card callback has chatId/topicId | Verify P2CardActionTrigger payload fields first |
| Session ID passing | Breaking FishuAppI interface | Structured result is internal to OpenCode, not on shared interface |
